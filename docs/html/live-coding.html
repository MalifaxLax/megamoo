03 · Live Programming

Three ways to get code into a verb, all of them instant.

Why there is no reload step

A verb body is a row in the database, and the executor reads it at call time. There is no compiled artefact, no import cache, and no module graph to invalidate. The moment a verb's code changes, the next player to type that command runs the new version.

This is not a convenience feature bolted on for developers — it is the direct consequence of storing code on objects, and it is what makes the MOO paradigm work in practice. You can fix a broken verb while the player who tripped over it is still standing there.

Instant means instant

There is no staging area. The moment a verb body is saved it is live for every connected player. On a world with people in it, test risky changes on a copy — megamoo.py mm.db scratch.db, then ./mm scratch.db, which finds its own free ports alongside the live world. Break it there.

In-game: @adverb and @program

Two commands, in that order. @adverb declares the verb — its names, abbreviation minimums, permissions, and auth level. @program opens the in-MOO editor for its body, which is where you type or paste Python.

@adverb #123.go_ @program #123.go_

Declaring the verb

@adverb[/hidden] <object>.<name[(min)][,alias...]> [with <perms> [base] [min=N] [auth=N]]
ExampleEffect
@adverb #7.look,lTwo names for one verb.
@adverb #2.examine(3),look(1),lPer-name abbreviation minimums.
@adverb #2.examine,x with rx min=3Permission string plus a global minimum.
@adverb #15.reset with rwx baseUse BaseVerb instead of MasterVerb.
@adverb/hidden #5.at_post_moveCreate it already hidden — the right form for a hook.
@adverb #3.@telq with rx auth=3Require gm3 to invoke.

Permission strings follow the usual pattern: r read, w write, x execute. rx is the default and is what almost every verb wants.

Editing the body

@program <object>.<verb> — aliased @prog and @code — opens the editor. Pasting a whole verb in at once works fine; this is the normal way to move code written elsewhere into the game. Related commands:

CommandDoes
+decompile <obj>.<verb>Print the verb's source exactly as stored — the ground truth for what is running.
+verbs <obj>List the verbs actually attached to an object.
@rmverb <obj>.<verb>Delete a verb.
@clear <obj>.<verb>Clear a verb's body without removing the declaration.

On disk: the auto-reload watcher

Verb files live at <moo_verb_path>/<objnum>/<verb>.py, where the base path comes from the #8.moo_verb_path property. That property stores a dotted, home-relative path — megamoo.moo verbs expands to ~/megamoo/moo verbs.

The database is the source of truth

Those files are developer-facing copies. Editing one does nothing on its own — the running game reads the database, not the disk. Something has to push the file in.

The watcher

Set MEGAMOO_DEV_AUTORELOAD_VERBS=true — which is what ./mm does — and the server polls the verb tree every two seconds, comparing modification times and pushing changed files into the live database. Save in your editor; the next invocation runs the new code.

$ ./mm mm.db Verb auto-reload watching /Users/you/megamoo/moo verbs (every 2.0s)

It is off in the code by default, which is what you want in production: a running world should not be rewritten by whatever is on disk. The launcher turns it on because a development world is exactly the case where you do want that. Starting the server any other way leaves it off unless you export the variable yourself — and it survives an in-game @restart, because the server re-execs with the environment it already had.

Syntax errors cannot break a running verb

The watcher compiles each changed file in isolation before installing it. A syntax error is logged and the previously-working version keeps serving. You will not take the game down with a stray colon — but do watch the log, because a verb silently failing to update looks exactly like a verb that did not change.

The initial scan only records modification times; it does not reload everything at boot, since the database already holds the current verbs. Only edits made while the server is running trigger a reload.

Loading files deliberately

CommandDoes
@reload <obj>.<verb>Load one verb from its file.
@reload <obj>Load every verb file for that object. If the directory does not exist yet, it is created and the object's verbs are exported to it.
@reload allSweep every numbered directory. Existing verbs are updated; missing ones are created.

The export behaviour is the easy way to get an object's verbs onto disk for editing in a real editor: @reload #123 once, and the files appear.

Watch the path when you copy a world

#8.moo_verb_path travels with the database. Copy a world to a differently-named directory and the watcher will still be pointed at the old one — verbs keep working, since they live in the database, but your disk edits quietly stop landing. Update the property after any rename.

Through the API

With the JSON API enabled (see Getting Started), set_verb writes directly to the live database — the same instant effect, driven by tooling rather than a person. get_verb, list_verbs, search_verbs and delete_verb round out the surface. This is what the MCP bridge is built on.

Working with an AI assistant

Verbs are unusually well suited to being written with an AI assistant, for a specific reason: they are small, self-contained Python files with a fixed namespace and no imports to resolve. A verb is a single-file problem with a tightly bounded context.

With the MCP bridge connected, an assistant is not reading your repository and guessing — it is holding the live world. It can read what properties #200 actually has, list the verbs a room really carries, write a verb with set_verb, run the command as a test character with run_command, read what the game printed back, and tail the log when it throws. The write–test–fix loop happens without a human in the middle retyping things.

What makes that work well in practice:

  • Point it at a scratch world. Start the throwaway database with ./mm scratch.db — it finds its own ports — then tell the assistant to work on scratch, so it edits that world and not the one you care about. Ask it to confirm which database it is on before it writes anything.
  • Say which object and which hook. "Add a go_ to #123 that refuses passage unless the player carries the brass key" is a complete specification. "Make the door locked" is not.
  • Name the conventions it cannot infer. Use msg not notify; pmatch in player verbs; check existent; return True from a hook to suppress the default; missing properties are not None. A CLAUDE.md in the repo carrying these rules pays for itself immediately.
  • Have it verify by playing. The point of run_command is that "it should work" becomes "here is the output". Ask for the transcript.
The API is wizard access

set_verb and eval_code run arbitrary Python against the live database. An assistant holding that token can do anything a super-wizard can, including to the world your players are standing in. Scope it to a scratch database and keep the token out of version control.
