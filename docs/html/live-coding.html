03 · Changing Things Live

Rewrite a command while people are using it.

On this page

  2. From inside the game
  3. From your own editor

Why there is no restart

Commands are not part of the program. They are stored in your world file, next to the rooms and the furniture, and they are read fresh each time someone types one. So changing a command is changing a thing in the world, not rebuilding the software — and it takes effect immediately, for everyone already logged in.

That is a genuinely different way to work. You do not reproduce a problem in a test copy: you stand next to the broken door, fix it, and try it again.

Instant means instant

There is no staging area. The moment you save a command it is live for every connected player. On a world with people in it, try risky changes on a copy first — megamoo.py mm.db scratch.db, then ./mm scratch.db, which finds its own free ports and runs alongside the real one.

From inside the game

Two commands, in that order. @adverb creates the command; @program opens an editor for what it does. Paste in what you like.

> @adverb #123.go_ > @program #123.go_

A few variations of the first one cover almost everything:

Written asGives you
@adverb #7.look,lOne command, two names.
@adverb #2.examine(3),xexa is enough to fire it.
@adverb/hidden #5.at_post_moveHidden from players — the right form for a hook.
@adverb #3.@telq with rx auth=3Only staff at level 3 may use it.

And to see what is really there:

CommandDoes
+verbs <obj>List the commands attached to something.
+decompile <obj>.<verb>Print exactly what is running — the ground truth.
@rmverb <obj>.<verb>Delete one.

From your own editor

The in-game editor is fine for small changes; for anything longer you will want a real editor. Commands can live as files on disk, under moo verbs/<object number>/<name>.py, and ./mm watches that folder: save a file, and the running game picks it up within a couple of seconds. No reload command, no restart.

$ ./mm mygame.db Verb auto-reload watching /Users/you/megamoo/moo verbs (every 2.0s)

To get an object's commands out onto disk in the first place, @reload #123 once — the folder is created and the files appear. After that, editing them is enough.

The database is the original

The files are a convenient copy; what actually runs lives in your world file. That is why a syntax error cannot take the game down — the broken file is refused and the previous working version keeps serving — and why copying a world to a new folder needs the watcher pointed at the new path (#8.moo_verb_path) or your edits quietly stop landing.

With an AI assistant

Commands suit this unusually well: each one is a short, self-contained file with no imports to chase. With the tooling connection open, an assistant is not reading your files and guessing — it is holding the live world. It can see what an object really has on it, write a command, run it as a test character, read what the game printed back, and check the log when something throws.

Three things make that work in practice:

  • Point it at a scratch world. Start a throwaway copy with ./mm scratch.db and tell the assistant to work on scratch. Ask it to confirm which world it is on before it writes anything.
  • Say which object and which behaviour. "Add a go_ to #123 that refuses passage unless the player is carrying the brass key" is a complete request. "Make the door locked" is not.
  • Have it check its own work by playing — walk into the door, read what the game said. A command that looks right and does nothing is the common failure, and only playing it catches that.
