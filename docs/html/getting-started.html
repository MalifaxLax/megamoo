Getting Started

Copy a database, crank it up, and you are running a world.

The whole idea

A MegaMOO world is its database file. The engine is stateless between runs: the code in moo/ is the machinery, and every room, object, character, and verb lives inside a single SQLite file. That one fact is what makes getting started trivial, and it is worth internalising before anything else, because it explains everything below.

The repository ships with mm.db — a starter world of 157 objects containing the core prototypes, the out-of-character lobby, a working character generator, one in-character room, and a wizard account. To start developing you copy that file and run the copy. That is the entire onboarding procedure.

$ python3 megamoo.py mm.db mygame.db # make your own world $ ./mm mygame.db # run it

Connect a MUD client — or just telnet localhost 6770 — and log in as wizard with the password megamoo. You are standing in the lobby of a world that is entirely yours to break.

./mm is the development launcher. Every run gets the same three things, none of which you have to type:

  • the JSON API enabled, with the token from ~/.megamoo/token — which is what lets an AI assistant drive the world;
  • verb auto-reload on, so editing a file under moo verbs/ pushes it into the running game;
  • no ports named, because the engine picks free ones.

It is only a convenience wrapper — python3 megamoo.py mygame.db runs the same server with none of those three, which is the right choice for a world with players on it. But ./mm is the form worth learning, because it is the one that does not change when you start running two worlds at once.

Change this first

The shipped wizard password is public knowledge — it is written in this manual. Change it with setpass before the server is reachable by anyone but you.

Copying a database

The two-argument form is a copy operation, not a launch. Given a source and a destination it loads the source read-only, writes a fresh database at the destination, copies every object across, prints where it put the result, and exits. It does not start the server. Running the new world is a separate second command.

$ python3 megamoo.py mm.db mygame.db Creating new database: mygame.db Created database with 157 objects Database created successfully at mygame.db Use this database to start the server: python megamoo.py mygame.db

Because a world is just a file, you can also copy one with cp. The built-in form is safer while a server is live, though: it opens the source read-only and rebuilds the target cleanly, whereas copying a running database with cp can capture a torn snapshot if the server happens to be writing at that moment.

Name the copy carefully

The second positional argument is guessed, not declared. A name containing a dot is only treated as a database if it ends in .db — so megamoo.py mm.db mygame.sqlite silently reads mygame.sqlite as a hostname to bind to and creates nothing. A bare number is read as a port, so megamoo.py mm.db 7777 runs mm.db itself rather than copying it. And an existing destination is overwritten with only a logged warning — no prompt.

Running several worlds at once

Nothing in the engine is global. Each server process owns exactly one database file and its own listening ports, so you can run as many worlds side by side as you like: a stable world for players, a scratch copy for an experiment you expect to ruin, and a third holding last week's backup so you can compare behaviour between them. They share no state and cannot interfere with each other.

$ ./mm mm.db & # the stable world — game 6770, API 7778 $ ./mm scratch.db & # somewhere to break things — game 6771, API 7779 $ ./mm backup.db & # last week, for comparison — game 6772, API 7780

The same command three times, with nothing to keep distinct. A world starts at the configured port (6770 for the game, 7778 for the API) and, if that one is taken, moves up to the next free one, saying so in the log: Port 6770 in use; auto-selected 6771. You are told where each world landed rather than having to decide in advance.

This is the workflow the copy command exists to serve. Testing a risky change does not mean backing up and restoring — it means copying the file, running the copy, and deleting it when you are done.

Which port did it get?

The startup log says, and so does the discovery file described below — and if you are working through an AI assistant, list_servers tells you every running world with its game and API port. Naming a port yourself still works and still wins: ./mm mm.db --port 6777 pins that exact port, and a collision then fails the boot instead of moving the world somewhere your players are not looking.

The JSON API

Beyond the player-facing Telnet port, a server can expose a second, line-oriented JSON API for tooling. It is off by default, binds to 127.0.0.1 only, and requires a token. ./mm turns it on for you and supplies the token:

$ ./mm mm.db mm: generated a new API token in /Users/you/.megamoo/token Server listening on 0.0.0.0:6770 API server listening on 127.0.0.1:7778

The token is generated once, on first run, and kept in ~/.megamoo/token — one secret shared by every world on the machine and by the MCP bridge below, so nothing has to be re-registered when you rotate it or add a world. Starting the server by hand is the same thing spelled out:

$ python3 megamoo.py mm.db --api --api-token "$(cat ~/.megamoo/token)"

The API runs inside the same event loop as the game, so its handlers hold a direct reference to the live database. Changes made through it take effect immediately, in the running world, with no reload — which is precisely what makes it useful as a tooling surface rather than an administrative afterthought.

You do not assign ports

Neither port is yours to allocate. The game starts at 6770 and the API at 7778, and each walks upward to the first free one, so running a second world is the same command again:

$ ./mm mm.db Server listening on 0.0.0.0:6770 API server listening on 127.0.0.1:7778 $ ./mm scratch.db Port 6770 in use; auto-selected 6771 API port 7778 in use; auto-selected 7779

The pair each world settled on is written to a discovery file — host, API port, game_port, pid, database path — so tools can find a server instead of being told where it is. The MCP bridge below reads it. It is deleted when the server shuts down, and one left behind by a crash is ignored, because the pid in it no longer names a live process.

megamoo.py writes that file beside the database (mm.db → mm.db.api.json). ./mm writes it into ~/.megamoo/run/ instead, which is what lets tooling see worlds you started from other directories; the bridge looks in both places.

When you do want a specific port

--port 6777 and --api-port 7900 pin those exact ports and turn the search off — naming a port means you want that port, so a collision is a startup error (address already in use, non-zero exit) rather than a silent move somewhere else. Use them when something outside MegaMOO — a firewall rule, a tunnel, a DNS entry, a fixed client config — depends on the number.

MCP: driving the world from an AI assistant

MCP — the Model Context Protocol — is a standard way for an AI coding assistant to call tools that someone else has written. MegaMOO ships one at tools/megamoo_mcp.py: a small bridge that presents the JSON API as a set of MCP tools, so an assistant such as Claude Code can inspect and modify your running world directly instead of guessing at it from source files.

The point is that the assistant is looking at the live world rather than the repository. It can read the actual property values on object #200, list the verbs a room really has, run a command as a test character and read what the game printed back, and tail the server log after a verb throws. Work that would otherwise be a loop of "edit a file, restart, reconnect, retype the command, squint at the output" collapses into the assistant doing it and reading the result.

ToolWhat it does
run_commandExecute a game command as a test character and return the output.
get_object, get_location, list_contentsInspect objects and where things are.
list_verbs, get_verb, set_verb, delete_verbRead and rewrite verb code in the live database.
list_properties, get_property, set_propertyRead and write properties.
search_verbs, search_objectsSearch the world by pattern or name.
eval_codeEvaluate arbitrary Python against the live database.
tail_log, server_statusRead the log and check whether the game is up.
list_servers, use_databaseSee every running world, and choose which one to work on.

Register the bridge with your assistant once. There is nothing to fill in — no port, no token:

$ claude mcp add megamoo -- python3 ~/megamoo/tools/megamoo_mcp.py

The token comes from ~/.megamoo/token, the same file ./mm starts every world with. Set -e MEGAMOO_API_TOKEN=… if you would rather be explicit; the environment wins over the file.

The bridge holds one lazy, auto-reconnecting connection, so it survives the game restarting underneath it. If the server is down entirely, the world-facing tools return a clear error rather than hanging — while tail_log and server_status keep working, since they read from disk. That is usually exactly when you need them.

The bridge works out the address each time it connects, reading the discovery file the running server wrote — so it follows a world that came back on a different port without being re-registered. In order: MEGAMOO_API_PORT if you set one, then a world chosen with use_database, then MEGAMOO_API_INFO (a named discovery file), then MEGAMOO_DB (that database's file), then the only live discovery file it can find, then 7778.

Working on one world when several are running

With one world up, discovery is unambiguous and there is nothing to configure. With several, tell the assistant which you mean, in words:

you: what worlds are running? assistant: two — mm.db (game 6770, API 7778) and scratch.db (game 6771, API 7779). you: work on scratch assistant: now on /Users/you/megamoo/scratch.db.

That is list_servers and use_database. The choice holds for the rest of the conversation, takes effect on the next call, and needs no restart of the assistant or the bridge. scratch, scratch.db and a full path all name the same world.

Know which world it is editing

Which database the assistant is pointed at decides which world your next verb rewrite lands in — worth confirming before you let it write anything. server_status always reports the database and port it is actually talking to, and if several servers are advertising and nothing says which, the bridge refuses to guess and lists what it found rather than picking one.

Treat the API as wizard access

eval_code and set_verb execute arbitrary Python against the live database. Anyone holding the token effectively owns the world. Keep it localhost-only, never commit it, and do not enable the API on a public-facing instance without understanding that.
