Prototypes and inheritance

Every object has exactly one parent, and inherits that parent's verbs and property defaults. The shipped database is a shallow tree of prototypes you build on rather than replace:

ObjectIs the parent of
#1 Root_ObjectEverything. Carries msg, msg_room, _title.
#10 BaseObjectThe root of in-world things.
#11 objectGeneric scenery; rooms and exits descend from it.
#12 itemAnything carriable.
#15 BaseRoom#16 OCRoom (out-of-character) and #17 ICRoom.
#20 BaseExit#21 directional, #22 walkable, #23 closable, #24 climbable, #25 jumpable.
#26 BaseContainer#27 chests, #28 cups and vessels.
#30 BaseFurnitureChairs, beds, tables.
#35 BaseWearableClothing.
#90 / #91Edibles and drinkables.
#92 BaseMerchantShopkeeper price books.
#3 Base_Character#4 OCharacter, #5 ICharacter. Carries every staff verb.

Create children with @make <parent> = <name>, and reparent with @parent <object> = <new parent>. The rule of thumb: if two objects need the same behaviour, it belongs on a shared parent. If exactly one object needs it, it belongs on that object — see the verb_ hooks.

Defining versus setting

A property must be defined on the prototype for children to inherit it. Setting a property on a template that was never defined there can silently fail to propagate to clones — if a spawned object is mysteriously missing a value, check that the parent actually declares it with @adprop.

Nouns and name_mod_list

An object's displayed name is not typed in directly. It is composed from a base noun plus a five-slot list called name_mod_list:

[article, adj1, adj2, adj3, trailer] ['a', 'old', '', '', '' ] -> "an old sword" ['the', '', '', '', '' ] -> "the sword" ['', '', '', '', '(broken)'] -> "sword (broken)"

The _title verb on #1 reassembles obj.name and obj.cname (the capitalised form) from these parts whenever they change, and corrects a to an automatically based on the first letter of whatever follows. Note that the correction keys off the adjective when one is present — which is why "a old sword" becomes "an old sword" rather than tracking the noun.

CommandSlot it edits
@name obj = swordThe noun itself.
@article obj = theSlot 0.
@adjective obj = old rustySlots 1–3 (up to three; omit the value to clear).
@trailer obj = (broken)Slot 4.
@title objRebuild the display name from the current parts.

This structure exists to serve the matcher. Because adjectives are discrete slots rather than words baked into a name string, blue is a fact about the object that can be tested, not a substring that has to be guessed at.

Match words come from the noun

Containers are titled bare on purpose. A case of whiskey is "a case", not "a case of fire whiskey", because the title feeds the matcher — put the contents in the title and drink whiskey starts matching the box. Describe contents in the description or via look in, never in the name.

Native attributes, not properties

noun and aliases are columns on the object row, not properties. Never @adprop them — set noun directly. Adding a property that shadows a native attribute produces confusing, hard-to-trace behaviour.

How the matcher finds an object

When a player types get the 2nd blue sword, the matcher decomposes that into three parts and tests candidates against all of them:

"sword" -> noun="sword" adjectives=[] ordinal=0 "blue sword" -> noun="sword" adjectives=["blue"] ordinal=0 "2nd blue sword" -> noun="sword" adjectives=["blue"] ordinal=1

The last token is the noun; everything before it is an adjective that must appear, in order, in the candidate's name or its adjectives property. A leading ordinal (2nd, third, 3) selects the Nth match. Articles are ignored.

There are two entry points, with deliberately different powers:

FunctionUse inUnderstands
bmatch()Staff verbsme, here, my X, ordinals, adjectives, plus #N dbrefs and $constants.
pmatch()Player verbsThe same, minus #N and $name.
# search room + inventory bmatch("sword", pobj, pobj.contents + pobj.location.contents) # search inside a specific container bmatch("gem", pobj, chest.contents) # "my" restricts to the player's own things bmatch("my key", pobj, [])
Use the right matcher

Calling bmatch() in a player-facing verb hands every player the ability to act on any object in the database by number — reaching into locked rooms, other people's inventories, anywhere. Player verbs use pmatch(). This is the single easiest security mistake to make in MegaMOO.

Also check existent

Every unhidden player verb should verify obj.existent == True after matching and treat a false result as no match. Recycled objects can linger in a candidate list; this is the guard against acting on a corpse.

Rooms match exits through match_exit on #15, which uses pmatch() and therefore supports ordinals — go 2 door works in a room with two doors.

Object numbers, @fon and @foff

New objects take the lowest unused, unreserved number — not the next number after the highest. Delete #150 and the next thing you create becomes #150, landing in the middle of whatever range you had carefully laid out. Reservation is how you stop that.

Reserved numbers are skipped by create() entirely. The starter database uses this: the gaps below #201 are reserved, so a developer's first @dig lands at #201 rather than filling a hole at #50.

Reserving a block outright

@reserve #500 to #599 # hands off this range @reserve /free #500 to #599 # release it @reserve /list # show reserved blocks

A personal working range: @fon / @foff

This pair exists for a builder who wants a private stretch of numbers to work in. Each staff member has a free_obj range on their character, and the two commands toggle whether the unused numbers in it are protected.

@fon/set 500 to 599 # claim a personal range @foff # RESERVE the unused numbers in it — protect them @fon # UNRESERVE them — release for general use @fon/list # show what's currently reserved and unused @fon/clear # forget the range
The names read backwards

@foff — "free off" — reserves, switching allocation off for those numbers. @fon — "free on" — unreserves, making them freely allocatable again. The verb is about whether the numbers are free to take, not about whether your reservation is on. Nearly everyone gets this backwards once.

The working pattern: @fon/set your range once, @foff to protect it while you build so nobody else's @dig lands inside it, and @fon when you are finished and the leftovers can go back into circulation.

@renumber <object> to <n> (gm5) moves an existing object to a specific number. It does not chase down references stored in other objects' properties — exits, plist, globals — so verify afterwards.
