04 · Auth & Hidden Verbs

Who may do what, and what is not a command at all.

The gm ladder

Authority is stored as a list of gmN strings on an object's auth property. auth_level() returns the highest level present, and sync_auth_flags() keeps the object's PROGRAMMER and WIZARD flags consistent with it — gm3 and above sets PROGRAMMER, gm4 and above sets WIZARD.

LevelRoleTypical powers
gm1Basic builder@color, @tel, hold, +show
gm2Advanced builder@dig, @open, @desc, @name, @move, @delete
gm3Programmer@adverb, @program, @set, eval, @make, @parent
gm4Wizard@delplayer
gm5Super-wizard@auth, @shutdown, @restart, @renumber, @reserve

Grant and revoke with @auth <player> = add|remove <level>. That command is gm5 only — the ability to hand out authority is itself the top of the ladder.

The levels are cumulative in effect but stored as a list, so a character can hold ['gm1', 'gm4']; auth_level() reports 4. The shipped wizard #100 carries ['gm5'].

Two enforcement mechanisms

These are independent, and it is worth knowing which one you are relying on.

1. The guard clause

Most staff verbs simply begin by checking, which is why an unauthorised player gets a flat "Do what?" rather than a permission error — the verb declines to admit it exists:

if auth_level(pobj) < 3: pobj.msg("Do what?") return

This is a convention, not a framework. It lives in the verb body, so it is visible in +decompile and easy to get wrong by omission. Every staff verb you write should open with one.

2. The verb's auth column

Separately, each verb row carries an auth level enforced by the engine before the body runs at all. Set it with:

@verbauth #3.@telq = 3 # require gm3 @verbauth #3.@telq # read the current setting @adverb #3.@mycmd with auth=3 # or set it at creation

Both walk the inheritance chain if the verb is not found locally. Belt and braces is normal: declare auth=N so the engine blocks the call, and keep the guard clause so the verb is safe if it is ever invoked programmatically.

Hidden verbs

Hiding is orthogonal to auth. A hidden verb is not invokable from the command line by anyone, regardless of level — it can only be reached programmatically through call_verb().

This is what internal hooks are for. go_, at_post_move, _title, _resource and the rest are machinery, not commands; a player typing go_ should get nothing at all.

@adverb/hidden #5.at_post_move # create it hidden @hideverb #5.at_post_move # or hide it afterwards @unhideverb #5.at_post_move # reverse it

By convention a leading underscore marks a verb as internal, and a trailing underscore marks a per-object hook. Neither convention is the enforcement — @hideverb is. A hook you forget to hide is a command players can type.

Verb shadowing

A verb defined lower in the inheritance chain wins over one defined higher, and this happens silently. No warning, no log line. It is the intended mechanism — it is how a specific object overrides a shared prototype — but it is also the bug you will actually hit, because an accidental name collision looks exactly like an intentional override.

When a command behaves in a way the code you are reading cannot explain, the question is always "which body is actually running?" Three commands answer it:

CommandTells you
+verbs <object>What is attached to this object specifically.
@examine <object>Parent, owner, properties and verbs together.
+decompile <obj>.<verb>The source that is really being executed.

The same trap catches consumables: a drink verb added to a vessel will shadow the shared one on the room prototype, and the shared one is where all the interesting behaviour lives. Prefer a drink_ hook over a drink override unless you genuinely mean to replace the command.
