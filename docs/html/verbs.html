The command pipeline

When a player sends a line, the server resolves it in stages. Understanding the order matters, because it explains both why abbreviations work and why a verb you just added is sometimes shadowed by one you forgot about.

  1. Split the command word from the rest of the line. Anything after the first space is the raw argument string.
  2. Strip MUSH-style switches. look/brief north yields verb look with switches = ['brief'].
  3. Find a matching verb by walking the object's own verbs and then up the inheritance chain, checking the command word against each verb's key and aliases.
  4. Parse the arguments using the matched verb's type, populating dobj, prep, iobj and friends.
  5. Run at_pre_cmd(), then func(), then at_post_cmd().

Abbreviation matching

Each verb name carries a min — the fewest characters that will match it. A min of 0 demands the full name. With min=3, @cre fires @create. The @ and + prefixes are matched separately and must agree, so @cre will never reach a verb named create.

@min #2.examine = 3 # 'exa' now matches @adverb #2.examine(3),look(1),l # or set it at creation

Object resolution — turning the 2nd blue sword into an actual object — is covered in Objects, Names & Numbers.

MasterVerb and the verb-type system

Every verb is backed by a verb type — a class that decides how the argument string is dissected before your code runs. There are two in the base hierarchy:

BaseVerb Minimal. Lifecycle hooks, name matching. No argument parsing. └── MasterVerb Adds full direct-object / preposition / indirect-object parsing.

MasterVerb is the default and the right answer nearly always. Its parse() splits the arguments on the first recognised preposition and hands your code a structured view:

Input dobj prep iobj --------------------------- ------------ ----------- --------- sword 'sword' '' '' blue sword from chest 'blue sword' 'from' 'chest' under old chest 'old chest' 'under' '' ball from under old bed 'ball' 'from under' 'old bed' #10 = Rusty Sword '#10' '=' 'Rusty Sword'

Single-character prepositions — =, :, ?, . — are tried first and do not need surrounding spaces, which is what makes @desc #14=A room parse identically to @desc #14 = A room. A second preposition, if present, populates prep2 and dobj2.

AttributeHolds

Reach for BaseVerb only when standard parsing is actively in your way — a verb whose argument is a free-form sentence that must not be split on the word "to", say, or one that wants a regex of its own. You then own parse() entirely.

Writing a custom verb type

A verb type is an ordinary Python class registered in a global registry keyed by dotted path. The database stores that string in the verb's parent_type column and resolves it back to the class on load, which is why a type must be importable at startup — put it in a module under moo/.

# moo/my_verb_types.py import re from .verb_types import MasterVerb, register_verb_type @register_verb_type class WhisperVerb(MasterVerb): key = 'whisper' aliases = ['wh'] min = 2 # 'wh' is enough help_text = 'Whisper privately to someone in the room.' perms = 'rx' # Split on 'to' only, ignoring every other preposition, # so "whisper meet me at the gate to guard" works. rexp = re.compile(r'\s+to\s+') def func(self): target = pmatch(self.iobj, self.pobj, self.location.contents) if not target: self.pobj.msg("Whisper to whom?") return self.pobj.msg(f'You whisper to {target.name}: {self.dobj}') target.msg(f'{self.pobj.name} whispers: {self.dobj}')

Class attributes

Attach a verb to the new type by passing its dotted path when you create the verb, or build a class at runtime with the define_verb() factory when it is not known until the game is running:

DrinkVerb = define_verb( 'drink', aliases = ['sip', 'quaff'], min = 2, parent = 'moo.verb_types.MasterVerb', func = lambda self: self.pobj.msg(f'You drink from {self.dobj}.'), )
A new type needs a restart

Verb code is data and loads instantly. A verb type is a Python class in the moo/ package, imported at boot — adding one is the rare case that genuinely requires bouncing the server. Plan types up front; iterate on verb bodies freely.

Inside a verb: the injected namespace

Verb files are not modules and have no imports of their own for game state. Instead the executor builds a namespace and runs your code inside it. Everything below is simply there:

GroupNames
Contextpobj (the player), this (the object the verb is on), caller, location, db, verb, args, argstr
Parsed partsdobj, prep, iobj, dobj2, prep2, lhs, rhs, switches, arglist, dobjlist, iobjlist
Game builtinsmove(), msg_room(), call_verb(), create(), recycle(), notify(), force(), search(), find(), auth_level(), pmatch(), bmatch()
Messaging defaultssub, dob, iob, uob, exclude
Utilitiessu (string utils), _effects (effects manager)
Safe PythonA curated subset — len, str, range, sorted, and so on. open, eval, exec, compile and __import__ are deliberately absent.

Two pieces of source rewriting happen before execution. #42 becomes a live object reference, and $name resolves a system constant ($eu is the effects utility, $item the item prototype). You can still import re or import random — the standard library is available — but reach for the injected builtins rather than poking the database directly.

Messaging

Send text with obj.msg(...) and obj.msg_room(...), never the raw notify() builtin. msg wraps notify and is overridable per object, which is how a deafened character or a screenreader user gets different treatment for free. Pass sub=pobj, dob=dobj, iob=iobj so the substitution engine can render pronouns and object names correctly for each observer.

pobj.msg("You pick up %d.", sub=pobj, dob=item) pobj.location.msg_room("%S picks up %d.", exclude=[pobj], sub=pobj, dob=item)

Tokens take either a % or $ prefix. Objects go through dob/iob as %d/%i; raw strings — numbers, coin words — go through s0=/s1= kwargs and render as %0/%1. Gender pronouns are %ps, %po and friends. +pron in-game prints the full table.

Three gotchas worth knowing early

Missing properties are not None. Reading an absent property returns a _null_attr sentinel that is falsy and whose repr is 'None' — but is None is always False against it. Test with == None, plain falsiness, or or.

Never reassign a call_verb kwarg name. Read it into a new variable first; rebinding the parameter corrupts the call context.

Escape % in raw output. Verbs that print stored values verbatim must double them to %%, or the substitution engine will eat them — %i is ANSI inverse.

The verb_ hook convention

This is the mechanism that makes per-object behaviour possible without special-casing anything centrally, and it is the most important idea in this chapter.

Shared commands live on the room prototypes. Before doing the default thing, they offer the matched object a chance to handle the command itself by calling a verb of the same name with a trailing underscore. If that hook exists and returns a truthy value, the shared verb stops. If it does not exist, the call fails harmlessly and the default proceeds.

# in the shared `go` verb on #16 (OCRoom) try: result = call_verb(exit, 'go_') # does this exit want to handle it? if result: return # yes — we're done except Exception: pass # no such verb: carry on normally call_verb(exit, 'invoke') # the default: walk through it

The portal in the lobby is exactly this. #51 is an ordinary exit, but it carries a go_ verb that presents a character menu and puppets the player into their selection, then returns True so the normal "walk through the exit" behaviour never runs. Nothing in the movement system knows the portal is special. The chargen arch on #7 works the same way.

So the recipe for "this one door needs to do something unusual" is never to edit the movement code. It is: @adverb #123.go_, write the behaviour, return True to suppress the default or a falsy value to let it run anyway. The exception lives on the exception.

Hooks should be hidden

A hook is machinery, not a command — a player typing go_ should get nothing. Create them with @adverb/hidden, or hide them afterwards with @hideverb. See Auth & Hidden Verbs.
