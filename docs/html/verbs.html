Every command in the game is a short file you can open and change.

What a command actually is

A command is called a verb, and a verb is a small Python file attached to an object. When someone types look, the game finds the verb named look and runs its file. That is the whole idea. There is no separate language to learn and no build step — save the file, and the next person to type the command runs your new version.

# the `read` verb on a book if not args: pobj.msg("Read what?") return pobj.msg(this.text or "There is nothing written on it.")

Two things are worth noticing. Nothing is imported: pobj (the person typing), this (the object the verb is on) and args (whatever they typed after the command) are simply there. And the file reads top to bottom like the action it describes — check for a problem, say something, stop.

How a typed line reaches your code

When someone sends a line, the game splits off the first word, looks for a verb of that name — first on the objects nearby, then on what those objects inherit from — and runs it, having already broken the rest of the line into useful pieces for you.

Names can be abbreviated. Each verb says how few letters will do: with three, @cre is enough for @create. Set it when you make the verb, or afterwards:

> @min #2.examine = 3 # 'exa' now matches
Why a new command sometimes seems ignored

The search stops at the first match. If a verb of that name already exists somewhere closer — on the object rather than what it inherits from — yours never gets a turn. It is nearly always a name collision, not a broken file.

Saying things

Use msg to tell one person something and msg_room to tell everyone else. Pass along who is involved, and the game writes each observer their own correct version — "You pick up the lamp" for them, "Ana picks up the lamp" for everyone watching:

pobj.msg("You pick up %d.", sub=pobj, dob=item) pobj.location.msg_room("%S picks up %d.", exclude=[pobj], sub=pobj, dob=item)

Making one object behave differently

This is the most useful idea in the manual, so it is worth the two minutes.

Ordinary commands like go and get live in one shared place, not on every object. Before doing the usual thing, a shared command offers the object a chance to handle it — by looking for a verb with the same name and a trailing underscore. If that hook exists and returns True, the shared command stops there. If there is no hook, nothing happens and the normal behaviour continues.

# inside the shared `go` command result = call_verb(exit, 'go_') # does this exit want to handle it? if result: return # yes — we're done call_verb(exit, 'invoke') # the default: walk through it

The portal in the lobby is exactly this. It is an ordinary exit that happens to carry a go_ verb: it shows a character menu, puts you into the character you pick, and returns True so the usual "walk through it" never runs. Nothing in the movement code knows the portal is special.

So the recipe for this one door needs to do something strange is never to edit the movement code. It is @adverb #123.go_, write what should happen, and return True to replace the normal behaviour — or nothing at all to let it carry on afterwards. The exception lives on the thing that is exceptional.

Hooks should be hidden

A hook is machinery, not a command — a player typing go_ should get nothing at all. Make them with @adverb/hidden, or hide them afterwards with @hideverb. See Who Can Do What.

Going further

Commands can also change how the typed line is broken up before your code sees it, and run set-up and clean-up steps around it. That is engine work rather than world-building: see Writing Verbs in docs/manual/ for the verb-type system.
