Developing & Building

Writing verbs, shaping objects, and changing a world while people are standing in it.

The MOO paradigm

Most game engines separate the world from the code that runs it: content lives in data files, behaviour lives in a compiled binary, and changing either means stopping, rebuilding, and starting again. A MOO collapses that distinction. The world is a graph of numbered objects held in a live database, and the code — every verb, every command, every bit of behaviour — is stored on those objects, in the same database, editable from inside the running game by anyone with sufficient authority.

The practical consequence is that building and programming stop being separate activities. Digging a room, hanging a description on it, and giving it a verb that does something nobody anticipated are the same kind of act, performed with the same tools, at the same time, while players are walking around in it. There is no deploy step because there is nothing to deploy to; the thing you are editing is the thing that is running.

This shapes how MegaMOO worlds get built. You are not writing an application that will later contain a world — you are growing a world that already exists, one object at a time, and shaping behaviour by attaching it where it belongs. A door that behaves oddly gets its own verb; it does not get a special case in a central movement module. Behaviour lives with the thing that has it.

Inheritance is what keeps that from becoming chaos. Every object descends from a parent, and verbs are inherited, so shared behaviour is written once high in the tree and specialised only where a particular object genuinely differs. The usual rhythm is: define the common case on a prototype, then override the exception on the one object that needs it. Nearly everything in this section is a variation on that sentence.

One thing to unlearn

Player commands are not defined on players. In MegaMOO they live on the room prototypes — #16 for out-of-character rooms and #17 for in-character ones — because the room is the context that decides what is possible. Character objects carry only staff verbs. If you go looking for look on the player object, you will not find it.
